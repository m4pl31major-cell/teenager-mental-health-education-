# 心桥计划：观点冒险

> 面向青少年的网页端 3D 合作心理情境模拟游戏。  
> 当前开发策略：先完成单人最小可玩 Demo，再逐步扩展多人联机和不同年龄段内容。

## 1. 项目目标

玩家在 3D 校园中探索，与 NPC 对话、收集线索、识别谣言和从众心理等有害观念，并通过挑战与剧情选择观察不同结果。

### 核心设计原则

- 游戏中的怪物象征有害观念或行为，不把受欺凌者或施害者本身简单怪物化。
- 不暗示受害者应为遭遇的欺凌负责。
- 对涉及持续欺凌、威胁或人身安全的情境，提供向可信任成年人寻求帮助的选项。
- 先做可运行、可测试的小功能，不一次性实现全部系统。
- 不因某个 Skill 的建议而随意更换已有技术栈。
- 优先复用仓库现有代码、依赖和素材。

## 2. 开始前：先检查仓库

本 README 不假设仓库已经采用某个技术栈。开始开发前，Codex 必须先检查：

1. `package.json`、锁文件和现有目录结构。
2. 当前框架、构建工具和 3D 渲染方案。
3. 已有页面、场景、角色、交互和测试。
4. 当前项目的启动、构建和测试命令。
5. 已有 Skills 及其安装方式。

如果项目已经可以运行，先在不修改代码的前提下尝试启动并记录结果。不要重复安装已有依赖。

## 3. 技术方向（以仓库实际情况为准）

如果仓库尚未建立技术栈，建议考虑：

- React：游戏菜单、对话、线索面板和 HUD。
- Three.js：浏览器端 3D 场景。
- JavaScript：游戏逻辑。
- Vite：本地开发和构建。
- Git：版本管理。

以上是建议，不是强制要求。若仓库已采用合理且可运行的方案，应优先沿用。

## 4. 本地运行方式

### 第一步：检查运行环境

安装适用于当前项目的 Node.js LTS 版本，并打开终端进入仓库根目录。

### 第二步：查看项目脚本

先检查 `package.json` 中的 `scripts` 字段。以下命令仅适用于具有对应脚本的项目。

### 第三步：安装依赖

优先根据仓库中已有的锁文件选择对应命令：

- 有 `package-lock.json`：`npm ci`
- 有 `pnpm-lock.yaml`：`pnpm install --frozen-lockfile`
- 有 `yarn.lock`：使用与项目 Yarn 版本相匹配的安装命令

不要为了使用某个命令而新增第二种包管理器或锁文件。若依赖安装失败，先报告错误并调查原因，不要连续尝试不相关的修复。

### 第四步：启动开发服务器

查看 `package.json` 的 `scripts`。如果存在 `dev` 脚本，通常可使用：

```bash
npm run dev
```

如果项目使用 pnpm 或 Yarn，则使用相应包管理器的 `dev` 命令。以仓库实际配置为准。

启动成功后，终端通常会显示本地访问地址。将该地址复制到浏览器中打开。

### 第五步：构建与测试

只有在 `package.json` 中存在相应脚本时，才运行：

```bash
npm run build
npm run test
```

若没有 `test` 脚本，不要声称测试已经通过；应说明目前没有配置自动化测试，并执行适当的手动验证。

## 5. 第一阶段：最小可玩 Demo

Demo 名称：**《最后一张合照》**

建议目标时长：5–8 分钟。

### 必须完成的功能

1. 一个小型 3D 校园区域。
2. 玩家可以移动，摄像机可以正常跟随。
3. 至少一个可互动 NPC。
4. 玩家靠近 NPC 后触发对话字幕。
5. 至少三条可收集线索。
6. 一个象征有害观念的挑战对象。
7. 至少一次攻击、闪避或简单互动挑战。
8. 玩家作出选择后，可以看到不同的剧情结果。
9. 有明确的开始方式和结束反馈。

### 暂时不做

- 多人联机和房间系统。
- 账号、数据库和云端存档。
- 复杂的 AI NPC。
- 大型开放世界。
- 完整的小学、初中、高中三套内容。
- 大规模付费模型、语音或素材服务接入。

## 6. 推荐开发顺序

每一步都要先运行和验证，再进入下一步。

### 阶段 0：项目审查

- 检查仓库和技术栈。
- 确认启动、构建和测试方法。
- 列出可复用代码与当前阻塞问题。
- 调查 Skills，但未经确认不得安装。

### 阶段 1：场景与控制

- 建立或整理游戏入口。
- 显示简单 3D 场景。
- 实现玩家移动。
- 实现摄像机控制。
- 检查窗口缩放和基本性能。

### 阶段 2：NPC 与线索

- 添加交互区域。
- 添加对话字幕和选择按钮。
- 添加线索收集状态。
- 让已收集线索能在界面中查看。

### 阶段 3：挑战与剧情

- 添加一个观念怪物或挑战对象。
- 实现简单的攻击、闪避或交互机制。
- 将收集到的线索用于剧情。
- 实现至少两个可观察的剧情结果。

### 阶段 4：打磨 Demo

- 增加开始、暂停或结束界面（按需要取舍）。
- 检查流程是否能够从开始走到结局。
- 修复控制、交互和显示问题。
- 写明已知问题与启动步骤。

### 阶段 5：多人联机（后续）

先比较 WebSocket 自建方案、Colyseus 等框架及托管服务，再作选择。确认方案前不安装专用联机 Skill，也不实现账号系统。

联机面向青少年时，必须额外评估个人信息保护、房间访问控制、聊天与用户生成内容管理、断线处理和适用地区的合规要求。

## 7. Codex 协作规则

执行任务时遵守以下规则：

1. **先检查，再修改。** 开始前先阅读相关文件，确认已有实现。
2. **小步提交。** 每次只实现一个清楚、可验证的功能。
3. **先说明计划。** 修改前简要列出准备修改的文件及原因。
4. **保持范围明确。** 不把当前任务扩展成无关重构。
5. **不猜测命令。** 以实际 `package.json` 和仓库文档为准。
6. **不虚报测试。** 只报告实际执行过的测试及其结果。
7. **错误先定位。** 遇到报错时，先复现并找原因，再做最小修复。
8. **保护凭证。** 不输出、提交或上传 Token、API Key、密码和 `.env` 内容。
9. **审查外部代码。** 不直接执行未知仓库中的安装脚本。
10. **解释给初学者。** 用中文说明如何启动、测试和判断成功。

## 8. 每个功能的完成标准

一个功能只有满足以下条件，才算完成：

- 功能可以按说明触发。
- 没有阻塞主流程的错误。
- 在浏览器中完成实际验证。
- 若有自动化测试，相关测试已运行并报告结果。
- 不破坏已有功能。
- 更新必要的使用说明。
- 清楚列出尚未解决的问题。

## 9. 推荐的 Codex 任务模板

每次只给 Codex 一个主要任务。可以复制以下模板：

```text
请根据仓库当前实际情况完成一个小任务。

任务：
[在这里写一个明确功能，例如：让玩家可以在 3D 场景中移动]

开始前：
1. 阅读相关代码和项目说明。
2. 确认现有实现，不要重复造轮子。
3. 简要列出准备修改的文件及原因。

执行要求：
- 尽量采用最小修改。
- 不擅自更换技术栈或新增无关依赖。
- 不执行未经审查的外部脚本。
- 如果遇到不确定的重大技术选择，先说明选项和影响。
- 修改后运行适用的检查或测试。

完成后用中文报告：
1. 改了什么。
2. 如何启动或操作。
3. 执行了哪些测试及结果。
4. 我应该在浏览器中看到什么。
5. 已知问题和下一步建议。
```
